# Phase 3 도전 과제: 스터디룸 관리와 조회 구현

> 💡 **학습 가이드**: 요구사항은 [Phase 3 명세](phase-3-study-rooms.md)에서 확인할 수 있습니다.
> 이 문서는 문제를 스스로 정의하고 고민하며 한 단계씩 해결해 나갈 수 있도록 돕는 **실습형 문제지**입니다.

---

## 🎯 전체 미션

스터디룸(Room)을 관리하고, 사용자가 활성 방의 목록과 상세 정보를 조회할 수 있는 백엔드 모듈을 설계하고 구현하세요.

---

## 🧩 [Problem 1] Room 도메인 모델 및 DB 설계하기

### 요구사항

1. 스터디룸 정보(이름, 설명, 수용인원, 활성화 여부, 생성/수정일시)를 담는 도메인 엔티티를 정의하세요.
2. Drizzle ORM을 이용해 `rooms` 테이블 스키마를 작성하고, 마이그레이션 SQL을 생성하세요.
3. 데이터베이스와 상호작용할 Repository 인터페이스(Port)와 Drizzle 구현체를 작성하세요.

### 🤔 고민해볼 질문

- `isActive` 필드는 왜 필요할까요? 물리적으로 행을 삭제(`DELETE`)하는 것과 어떤 차이가 있을까요?
- 수용인원(`capacity`)은 어떤 제약조건(예: 0 이하 불가)을 가져야 할까요?
- 엔티티의 ID는 어떤 형식(UUID vs Auto Increment ID)을 사용하는 것이 유리할까요?

### 🧪 자가 검증 체크리스트

- [ ] Room 생성 시 기본적으로 `isActive`가 `true`로 설정되는가?
- [ ] Drizzle 마이그레이션을 실행했을 때 DB에 `rooms` 테이블이 정상 생성되는가?
- [ ] Repository 단위/통합 테스트에서 Room 생성, ID로 조회, 목록 조회가 정상 동작하는가?

---

## 🧩 [Problem 2] 관리자용 스터디룸 관리 API 구현하기

### 요구사항

1. `ADMIN` 권한을 가진 사용자만 접근할 수 있는 룸 생성, 수정, 비활성화 API를 구현하세요.
   - `POST /admin/rooms`: 방 생성
   - `PATCH /admin/rooms/:id`: 방 정보 수정 및 활성 상태 변경
   - `DELETE /admin/rooms/:id`: 방 비활성화
2. 요청 데이터의 유효성을 검증(Validation)하세요.

### 🤔 고민해볼 질문

- Phase 2에서 구현한 `AuthGuard`와 `RolesGuard`를 어떻게 조합하여 ADMIN 전용 엔드포인트를 보호할 수 있을까요?
- 스터디룸 이름을 빈 문자열로 보내거나 수용인원을 음수로 보내면 어떻게 방어해야 할까요?
- `DELETE` 요청 시 실제로 DB 행을 삭제할까요, 아니면 `isActive = false`로 수정할까요?

### 🧪 자가 검증 체크리스트

- [ ] 로그인하지 않거나 토큰이 없으면 `401 Unauthorized`가 발생하는가?
- [ ] `USER` 역할 토큰으로 요청 시 `403 Forbidden`이 발생하는가?
- [ ] `ADMIN` 역할 토큰으로 요청 시 정상적으로 방이 생성/수정/비활성화되는가?

---

## 🧩 [Problem 3] 사용자용 스터디룸 조회 API 구현하기

### 요구사항

1. 일반 사용자가 접근할 수 있는 스터디룸 조회 API를 구현하세요.
   - `GET /rooms`: 활성화된(`isActive: true`) 방 목록 조회 (페이지네이션 지원)
   - `GET /rooms/:id`: 특정 방 상세 조회
2. 비활성화된 방은 일반 조회 목록에 노출되지 않아야 합니다.

### 🤔 고민해볼 질문

- 목록 조회 시 페이지네이션(Page, Limit)과 전체 개수(Total Count)를 어떻게 계산하여 응답 구조를 만들까요?
- 존재하지 않는 방 ID를 조회할 때 어떤 에러와 상태 코드를 반환해야 할까요?

### 🧪 자가 검증 체크리스트

- [ ] 비활성화(`isActive: false`)된 방은 `GET /rooms` 목록에서 제외되는가?
- [ ] 존재하지 않는 ID로 `GET /rooms/:id` 요청 시 `404 Not Found`가 반환되는가?

---

## 🧩 [Problem 4] E2E 통합 테스트로 전체 흐름 검증하기

### 요구사항

관리자 방 생성부터 사용자 조회·방 비활성화까지의 전체 시나리오를 검증하는 E2E 테스트(`apps/api/test/rooms.e2e-spec.ts`)를 작성하세요.

### 검증 시나리오

1. ADMIN 계정으로 방 "스터디룸 101호" 생성 (`POST /admin/rooms`)
2. 일반 사용자 계정으로 방 목록 조회 (`GET /rooms`) → 방 1개 확인
3. 방 상세 조회와 관리자 방 수정 결과 확인
4. ADMIN 계정으로 방 비활성화 (`DELETE /admin/rooms/:id`)
5. 일반 사용자 목록 조회 (`GET /rooms`) → 방 목록에서 제외 확인
6. 비활성 방의 상세 조회에 정한 접근 정책이 적용되는지 확인
