# Phase 4: 기본 예약·트랜잭션과 예약 가능 시간

## 목표와 시작 조건

[Phase 3](phase-3-study-rooms.md)의 방 관리·조회와 관련 검증을 마친 뒤 진행합니다. 예약을 저장·생성하고 특정 방·날짜의 확정 예약을 조회할 수 있게 만든 다음, 실제 예약을 반영한 가용 시간 조회를 구현합니다.

전체 서비스 규칙은 [요구사항](requirements.md), 엔드포인트는 [API 초안](api-draft.md)을 참고합니다. 이 문서는 구현 순서와 아래 확정 예약 시간 정책을 정리합니다.

## 확정 예약 시간 정책 — 2026-10-02

사용자가 정책 결정을 위임하여 확정한 Phase 4 구현 기준이다. 기존 문서·코드의 운영 종료 18시/22시와 예약 길이 1시간/최대 2시간 차이는 **09~22시 운영, 정확히 1시간 예약**으로 통일한다. 이 기록은 정책 확정이며 구현 완료를 뜻하지 않는다.

| 항목 | 정책 |
| --- | --- |
| 기준 시간대 | 날짜, 운영 시간과 정각 여부는 모두 `Asia/Seoul` 기준이다. |
| 운영 시간 | 모든 방은 매일 09:00~22:00 운영한다. 주말도 동일하며 방별 시간·휴무일은 이번 단계에서 두지 않는다. |
| 시작 시각 | 09:00부터 21:00까지 매시 정각만 허용한다. 분·초·밀리초는 모두 0이어야 한다. |
| 예약 길이 | 정확히 60분이다. `endsAt = startsAt + 1시간`이며 마지막 슬롯은 21:00~22:00이다. |
| 예약 가능 기간 | 서울 기준 오늘부터 29일 뒤까지, 총 30개의 날짜다. 현재 시각에서 720시간을 더하는 방식이 아닌 달력 날짜 기준이다. |
| 당일 예약 | `startsAt > now`일 때만 가능하다. 정확히 시작 시각이거나 이미 시작한 슬롯은 예약할 수 없다. 별도의 최소 사전 예약 시간은 없다. |
| 시간 구간 | `[startsAt, endsAt)`로 취급한다. 09~10시와 10~11시는 겹치지 않으므로 연속 예약이 가능하다. |
| 예약 대상 | 활성 방만 예약할 수 있다. 같은 방·시간의 확정 예약과 같은 사용자의 시간 중복 예약은 허용하지 않는다. |
| 사용자 취소 | 기존 규칙대로 `now < startsAt - 10분`일 때만 가능하다. 정확히 10분 전부터 금지한다. |
| API 시간 입력 | `startsAt`, `endsAt`은 `Z` 또는 명시적 UTC offset을 포함한 ISO 8601 datetime으로 받는다. offset 없는 datetime은 거부한다. 동일 순간을 나타내는 서로 다른 offset은 동일하게 처리하고 서울 시각으로 정책을 검증한다. |
| DB 저장·API 출력 | DB에는 UTC 기준의 순간을 저장한다. API 시간 응답은 UTC의 `Z` 형식으로 통일한다. |
| 가용성 조회 날짜 | `date=YYYY-MM-DD`는 서울 날짜로 해석한다. 실제 달력에 없는 날짜나 형식이 잘못된 값은 400이다. |

### 가용 시간 조회

- 활성 방의 유효한 날짜를 조회하면 09~22시의 1시간 슬롯 **13개**를 시작 시각 오름차순으로 반환한다.
- 오늘부터 29일 뒤까지의 날짜에서 `startsAt > now`이고 같은 방·슬롯에 `CONFIRMED` 예약이 없으면 `isAvailable: true`다.
- 오늘 이미 시작한 슬롯과 과거 날짜의 모든 슬롯은 `isAvailable: false`다. 과거 날짜도 13개 슬롯을 반환한다.
- 오늘부터 30일 뒤 이상의 날짜 조회는 422로 거부한다. 예약 생성도 동일한 기간 제한을 적용한다.
- `isAvailable`은 방·슬롯의 가용성이다. 조회한 사용자가 다른 방에 같은 시간 예약을 가진 경우는 예약 생성 시 별도로 검증한다.
- 비활성 방의 가용 시간 조회에는 Phase 3에서 확정한 상세 조회 접근 정책을 적용한다. 비활성 방에 예약을 생성하는 요청은 기존 요구사항대로 422다.
- 가용성은 파생 값이며 별도 상태 컬럼으로 저장하지 않는다. 조회 후 다른 요청이 예약할 수 있으므로 생성 시 재검증과 DB 제약조건이 필요하다.

### 입력 거부 기준

- API 입력 형식 오류(시간대 누락, 잘못된 날짜·datetime)는 400이다.
- 시간 정책 위반(정각이 아님, 운영 시간 밖, 1시간이 아님, 이미 시작한 시간, 예약 가능 기간 밖)은 422다. 즉, 시작 시각이 현재 시각과 같거나 더 이르면 거부한다.
- 방 또는 사용자 예약 충돌, 취소 제한 위반과 재취소는 기존 요구사항대로 409다.
- 현재 시각은 서버 시각을 사용하고, 요청의 시간 정책 판단에는 동일한 기준 시각을 사용한다. 예약 생성 검증에서 시간 정책을 평가한 시각이 기준이다.

### 경계 예시

아래 값은 이해를 위한 서울 시각이며 API 응답에서는 UTC `Z`로 표현한다.

| 조건 또는 요청 | 결과 |
| --- | --- |
| 09:00~10:00, 21:00~22:00 | 운영 시간과 길이 조건 통과 |
| 08:00~09:00, 22:00~23:00 | 운영 시간 위반 |
| 09:30~10:30 | 정각 시작 위반 |
| 09:00~11:00 | 1시간 길이 위반; 연속 2시간 이용은 별도의 두 예약으로 처리 |
| 현재 09:00:00, 오늘 09:00 시작 | 시작 시각이 현재 시각과 같아 거부 |
| 현재 09:00:00, 오늘 10:00 시작 | 시간 조건 통과 |
| 오늘이 2026-10-02 | 2026-10-31까지 예약 가능, 2026-11-01부터 거부 |
| 10:00 시작 예약, 현재 09:49:59 | 사용자 취소 가능 |
| 10:00 시작 예약, 현재 09:50:00 | 사용자 취소 불가 |
| `2026-10-03T00:00:00Z` | 서울 2026-10-03 09:00 시작으로 검증 |

### 선택 이유

공통 운영 시간과 정각 1시간 슬롯은 기존 요구사항에 맞으며, 가용 시간·중복 예약·향후 동일 슬롯 대기열의 기준을 단순하게 유지한다. 30일의 예약 가능 기간은 조회·예약 범위를 제한하면서 충분한 사전 예약을 제공하기 위한 이번 설계 선택이다. 휴무일, 방별 운영 시간과 가변 예약 길이는 별도 요구가 생길 때 정한다.

## 수행 순서

1. **예약 시간 정책 확정**
   - [ ] 운영 시간, 정각 시작, 예약 길이와 과거 시간 판단 기준을 정리한다.
   - [ ] 기존 Phase 3 명세의 운영 종료 22시와 `apps/api/src/domains/reservations/domain/reservation.policy.ts`의 18시를 일치시킨다.
   - [ ] 요구사항의 정확히 1시간 예약과 코드의 최대 2시간 예약 차이를 정리한다.
   - [ ] DB 저장은 UTC, API 표현은 ISO 8601로 통일하고 날짜는 Asia/Seoul 기준으로 처리한다.
2. **예약 저장 기반**
   - [ ] Reservation 엔티티와 상태 전이를 구현한다.
   - [ ] 예약 테이블·마이그레이션과 Repository를 구현한다.
   - [ ] 같은 방·시간의 중복 확정 예약을 DB 제약조건으로 방지한다.
3. **예약 생성**
   - [ ] 활성 방의 미래 시간대에 `CONFIRMED` 예약을 생성한다.
   - [ ] 방의 예약 충돌과 사용자의 예약 시간 중복을 검증한다.
4. **확정 예약 조회**
   - [ ] 특정 방·날짜의 확정 예약을 조회한다.
5. **예약 가능 시간 조회**
   - [ ] 운영 시간과 예약 단위에 맞는 시간대를 생성한다.
   - [ ] 확정 예약과 과거 시간을 반영해 `isAvailable`을 계산한다.
   - [ ] 비활성 방의 접근 정책을 적용한다.
   - [ ] `GET /rooms/:roomId/availability?date=YYYY-MM-DD`를 연결한다.
6. **내 예약 조회·취소**
   - [ ] 내 예약 목록·상세 조회와 본인 예약 취소를 구현한다.
   - [ ] 취소 제한과 상태 전이를 검증하고 취소 이력을 보존한다.
7. **트랜잭션과 재요청 검증**
   - [ ] idempotency key의 필요성을 실험하고 결정한다.
   - [ ] 트랜잭션 실패 시 부분 저장이 남지 않는지 확인한다.

## 가용 시간 계산 규칙

가용성은 별도의 상태 컬럼으로 저장하지 않고 방의 활성 상태, 운영 시간, `CONFIRMED` 예약과 현재 시각을 바탕으로 계산합니다. 확정 예약이 있거나 지난 시간대는 `isAvailable: false`로 표시합니다. 확정 정책에 따라 하루 13개의 슬롯을 생성합니다.

아래 응답은 확정 정책에 따른 일부 시간대의 표현 예시입니다.

#### 📌 Availability 응답 예시 (`GET /rooms/:id/availability?date=2026-08-20`)

```json
{
  "roomId": "018f...",
  "date": "2026-08-20",
  "slots": [
    {
      "startsAt": "2026-08-20T00:00:00Z",
      "endsAt": "2026-08-20T01:00:00Z",
      "isAvailable": true
    },
    {
      "startsAt": "2026-08-20T01:00:00Z",
      "endsAt": "2026-08-20T02:00:00Z",
      "isAvailable": false
    }
  ]
}
```


## 가용 시간 조회 실습: 특정 날짜의 예약 가능 시간(Availability) 조회하기

### 요구사항

1. 특정 방과 날짜를 기준으로 시간대별 예약 가능 여부를 반환하는 API를 구현하세요.
   - `GET /rooms/:id/availability?date=YYYY-MM-DD`
2. **운영 정책**:
   - 앞 단계에서 확정한 운영 시간과 예약 단위 정책을 사용합니다. 날짜는 Asia/Seoul을 기준으로 해석합니다.
   - 해당 날짜/시간에 이미 `CONFIRMED` 상태의 예약이 있거나, 이미 지난 과거 시간대라면 `isAvailable: false`로 계산합니다.

### 🤔 고민해볼 질문

- 예약 가능 여부는 DB에 별도 컬럼으로 저장되어 있지 않습니다. 어떻게 실시간으로 계산할 수 있을까요?
- 클라이언트가 요청한 날짜(`YYYY-MM-DD`)를 `Asia/Seoul` 기준의 운영 시간 내 슬롯들(UTC 타임스탬프)로 어떻게 변환할 수 있을까요?
- 오늘 날짜를 조회할 때, 이미 지나간 오전 시간대는 어떻게 `isAvailable: false`로 처리할 수 있을까요?
- 비활성화된 방에 대해 가용성을 조회하려고 하면 어떻게 처리해야 할까요?

### 🧪 자가 검증 체크리스트

- [ ] 확정한 운영 시간과 예약 단위에 맞는 슬롯이 생성되는가?
- [ ] 예약이 없는 미래 날짜 조회 시 모든 슬롯의 `isAvailable`이 `true`인가?
- [ ] 과거 날짜를 조회하거나 오늘 중 이미 지난 시간대는 `isAvailable`이 `false`로 나오는가?
- [ ] 비활성 방 요청 시 적절한 에러(`422` 또는 `404`)가 발생하는가?

## 완료 조건

- [ ] 순차 요청에서 중복 예약이 생성되지 않는다.
- [ ] 남의 예약 조회·취소가 거부된다.
- [ ] 비활성 방·과거 시간 예약과 재취소가 올바르게 실패한다.
- [ ] 취소 이력이 남고 트랜잭션 실패 시 부분 저장이 없다.
- [ ] 애플리케이션 검증과 DB 제약조건의 역할을 설명할 수 있다.
- [ ] 비활성 방·과거 시간·확정 예약이 있는 시간을 예약 가능으로 노출하지 않는다.
- [ ] 날짜 경계와 시간대 처리가 일관적이다.
- [ ] 예약 생성·취소 결과가 가용 시간 조회에 반영된다.
- [ ] 관련 단위·통합·E2E 테스트가 성공한다.

## 통합 검증 흐름

방 생성 → 미래 날짜의 가용 시간 조회 → 예약 생성 → 해당 시간 예약 불가 확인 → 허용된 시점에 예약 취소 → 해당 시간 예약 가능 확인 순서로 검증합니다. 비활성 방 접근과 권한·시간 정책 실패 사례도 검증합니다.
