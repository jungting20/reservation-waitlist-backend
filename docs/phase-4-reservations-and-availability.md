# Phase 4: 기본 예약·트랜잭션과 예약 가능 시간

## 목표와 시작 조건

[Phase 3](phase-3-study-rooms.md)의 방 관리·조회와 관련 검증을 마친 뒤 진행합니다. 예약을 저장·생성하고 특정 방·날짜의 확정 예약을 조회할 수 있게 만든 다음, 실제 예약을 반영한 가용 시간 조회를 구현합니다.

전체 서비스 규칙은 [요구사항](requirements.md), 엔드포인트는 [API 초안](api-draft.md)을 참고합니다. 이 문서는 구현 순서를 정리하며, 기존의 미결정 정책을 새로 확정하지 않습니다.

## 수행 순서

1. **예약 시간 정책 확정**
   - [ ] 운영 시간, 정각 시작, 예약 길이와 과거 시간 판단 기준을 정리한다.
   - [ ] 기존 Phase 3 명세의 운영 종료 22시와 `apps/api/src/domains/reservations/domain/reservation.policy.ts`의 18시를 일치시킨다.
   - [ ] 요구사항의 정확히 1시간 예약과 코드의 최대 2시간 예약 차이를 정리한다.
   - [ ] DB 저장은 UTC, API 표현은 ISO 8601로 통일하고 날짜는 Asia/Seoul 기준으로 처리한다.
2. **예약 저장 기반**
   - [ ] Reservation 엔티티와 상태 전이를 구현한다.
   - [ ] 예약 테이블·마이그레이션과 Repository를 구현한다.
   - [ ] 같은 방·시간의 중복 확정 예약을 DB 제약조건으로 방지한다.
3. **예약 생성**
   - [ ] 활성 방의 미래 시간대에 `CONFIRMED` 예약을 생성한다.
   - [ ] 방의 예약 충돌과 사용자의 예약 시간 중복을 검증한다.
4. **확정 예약 조회**
   - [ ] 특정 방·날짜의 확정 예약을 조회한다.
5. **예약 가능 시간 조회**
   - [ ] 운영 시간과 예약 단위에 맞는 시간대를 생성한다.
   - [ ] 확정 예약과 과거 시간을 반영해 `isAvailable`을 계산한다.
   - [ ] 비활성 방의 접근 정책을 적용한다.
   - [ ] `GET /rooms/:roomId/availability?date=YYYY-MM-DD`를 연결한다.
6. **내 예약 조회·취소**
   - [ ] 내 예약 목록·상세 조회와 본인 예약 취소를 구현한다.
   - [ ] 취소 제한과 상태 전이를 검증하고 취소 이력을 보존한다.
7. **트랜잭션과 재요청 검증**
   - [ ] idempotency key의 필요성을 실험하고 결정한다.
   - [ ] 트랜잭션 실패 시 부분 저장이 남지 않는지 확인한다.

## 가용 시간 계산 규칙

가용성은 별도의 상태 컬럼으로 저장하지 않고 방의 활성 상태, 운영 시간, `CONFIRMED` 예약과 현재 시각을 바탕으로 계산합니다. 확정 예약이 있거나 지난 시간대는 `isAvailable: false`로 표시합니다. 하루의 슬롯 수는 확정한 시간 정책에서 도출하며, 기존 명세의 13개를 고정 완료 기준으로 사용하지 않습니다.

아래 응답은 일부 시간대의 표현 예시이며 운영 종료 시각을 확정하지 않습니다.

#### 📌 Availability 응답 예시 (`GET /rooms/:id/availability?date=2026-08-20`)

```json
{
  "roomId": "018f...",
  "date": "2026-08-20",
  "slots": [
    {
      "startsAt": "2026-08-20T09:00:00+09:00",
      "endsAt": "2026-08-20T10:00:00+09:00",
      "isAvailable": true
    },
    {
      "startsAt": "2026-08-20T10:00:00+09:00",
      "endsAt": "2026-08-20T11:00:00+09:00",
      "isAvailable": false
    }
  ]
}
```


## 가용 시간 조회 실습: 특정 날짜의 예약 가능 시간(Availability) 조회하기

### 요구사항

1. 특정 방과 날짜를 기준으로 시간대별 예약 가능 여부를 반환하는 API를 구현하세요.
   - `GET /rooms/:id/availability?date=YYYY-MM-DD`
2. **운영 정책**:
   - 앞 단계에서 확정한 운영 시간과 예약 단위 정책을 사용합니다. 날짜는 Asia/Seoul을 기준으로 해석합니다.
   - 해당 날짜/시간에 이미 `CONFIRMED` 상태의 예약이 있거나, 이미 지난 과거 시간대라면 `isAvailable: false`로 계산합니다.

### 🤔 고민해볼 질문

- 예약 가능 여부는 DB에 별도 컬럼으로 저장되어 있지 않습니다. 어떻게 실시간으로 계산할 수 있을까요?
- 클라이언트가 요청한 날짜(`YYYY-MM-DD`)를 `Asia/Seoul` 기준의 운영 시간 내 슬롯들(UTC 타임스탬프)로 어떻게 변환할 수 있을까요?
- 오늘 날짜를 조회할 때, 이미 지나간 오전 시간대는 어떻게 `isAvailable: false`로 처리할 수 있을까요?
- 비활성화된 방에 대해 가용성을 조회하려고 하면 어떻게 처리해야 할까요?

### 🧪 자가 검증 체크리스트

- [ ] 확정한 운영 시간과 예약 단위에 맞는 슬롯이 생성되는가?
- [ ] 예약이 없는 미래 날짜 조회 시 모든 슬롯의 `isAvailable`이 `true`인가?
- [ ] 과거 날짜를 조회하거나 오늘 중 이미 지난 시간대는 `isAvailable`이 `false`로 나오는가?
- [ ] 비활성 방 요청 시 적절한 에러(`422` 또는 `404`)가 발생하는가?

## 완료 조건

- [ ] 순차 요청에서 중복 예약이 생성되지 않는다.
- [ ] 남의 예약 조회·취소가 거부된다.
- [ ] 비활성 방·과거 시간 예약과 재취소가 올바르게 실패한다.
- [ ] 취소 이력이 남고 트랜잭션 실패 시 부분 저장이 없다.
- [ ] 애플리케이션 검증과 DB 제약조건의 역할을 설명할 수 있다.
- [ ] 비활성 방·과거 시간·확정 예약이 있는 시간을 예약 가능으로 노출하지 않는다.
- [ ] 날짜 경계와 시간대 처리가 일관적이다.
- [ ] 예약 생성·취소 결과가 가용 시간 조회에 반영된다.
- [ ] 관련 단위·통합·E2E 테스트가 성공한다.

## 통합 검증 흐름

방 생성 → 미래 날짜의 가용 시간 조회 → 예약 생성 → 해당 시간 예약 불가 확인 → 허용된 시점에 예약 취소 → 해당 시간 예약 가능 확인 순서로 검증합니다. 비활성 방 접근과 권한·시간 정책 실패 사례도 검증합니다.
